# Native Registry

Generated by `tools/Generate-NativeRegistry.ps1`. Do not edit by hand.

353 routines are admitted for every naturally observed call at
their address. Across those routes 3,270,046 of 3,328,944 observed
calls (98.2%) were proven native; the remainder fall back to emulated
assembly by design, because the dispatcher returns no replacement for a
state it has not been proven against.

The resulting state census is byte-identical to the assembly-only
baseline (`9036a9de…`), so that 41.02% is faithful, not merely running.
Two admitted routines are withheld from that run because each changes the
census on its own — `02:57E9` and `03:6054`. Both are proven `@all` on an
unpatched route, but their regressions assert a census hash that differs
from the baseline, so the change was blessed per-routine and is inherited
by any run that deploys them. Adding them back with explicit hooks still
completes 3,600 frames, at a census (`fe61e05b…`) that is not the
assembly one.

The hold-back is not a flag on the measurement command: it lives in
`kWithheldRoutines` in `src/app/main.cpp` and applies to every composed
deployment, so the interactive host runs the same faithful 351 that this
measurement does. Each run names them in its deployment summary.

## Cycle budget

A whole-ROM `--instruction-profile` of the same deployed route (6,904
executed addresses, 1,292,378,139 master cycles) shows what the
remainder is:

| Category | Master cycles | Share of all cycles | Share of working cycles |
| --- | ---: | ---: | ---: |
| Frame-sync spin loop (`00:E2FB`–`E39C`) | 584,757,771 | 45.25% | — |
| Timer sound driver (`00:FC00`–`FE48`) | 172,668,540 | 13.36% | 24.40% |
| Transcripts resumed after its RTI | 87,303,720 | 6.76% | 12.34% |
| Music sequencer (bank `45`) | 45,475,305 | 3.52% | 6.43% |
| Video banks (`08`, `09`) | 96,288,942 | 7.45% | 13.61% |
| Gameplay pool | 313,405,062 | 24.25% | 44.29% |

Nearly half the machine is idle: `00:E323` is `CMP $00` / `BEQ -4`,
spinning on the VBlank counter 24.2 million times. That is the game
waiting, not working, so it is not a porting target and it is the slack
that absorbs anything the port makes faster.

The second row needs the third to read honestly. The profile charges each
address the span to the next instruction hook, and the driver ends in an
`RTI` that returns into whatever the timer interrupted. When that is a
suspended checkpointed transcript, the rest of it replays with no hook in
between, so those cycles land on the driver's `RTI`: `00:FC8D` shows 347
master cycles per execution against a real cost of 21. Those 82,014,828
cycles are other routines' native bodies, already counted as native, not
sound-driver work. Every other address in the driver profiles at a clean
6, 12, 15, 18 or 21.

## The sound driver

The timer interrupt handler is the sound driver, and it now runs
natively. It is a flat state machine over `00:FC00`–`00:FE48` with no
subroutine calls at all: three PSG channels walked at X = 4, 2 and 0,
each streaming five-bit DDA samples out of a sequence bank mapped into
MPR6 with `TAM #$40` and pushed through the PSG waveform port at
`$0806`. The eight banks it selects between are listed in ROM at
`$FC06`, immediately ahead of the handler's first instruction.

Earlier reports placed bank `45` here and called it the PSG driver. That
was wrong. `$FC06` holds `48 49 4A 4B 4C 4D 4E 4F`, so the driver's data
banks are `48`-`4F`, mapped at `$C000` and only ever read. Bank `45`
runs at `$4000`-`$4CB8` and is the music sequencer, a separate component
that programmes the PSG registers `$0801`-`$0809` directly. It has its
own section below.

Taking it needed the transaction write channel widened past work RAM and
the four VDC ports. It now also carries the PSG register file
`$0800`-`$0809`, the timer at `$0C00`-`$0C01`, and the interrupt
controller at `$1402`-`$1403`. Each is a whole register file on the
hardware page whose writes are ordinary stores with no wait state, so a
transcript prices them like any other instruction — unlike the VDC
ports, which cost three extra cycles. Device writes are invisible to
a work-RAM census, so `--bus-write-range` and `--bus-write-trace` were
added to census them directly. The state census would catch a wrong
value on its own, since it hashes the audio as well as work RAM, but
only as a changed hash somewhere in 3,600 frames. The regression
asserts all 954,241 PSG, timer and interrupt-acknowledge writes,
byte-identical to assembly.

Two things bound what the transcript may cover. From the `CLI` at
`$FC32` the handler is interruptible, and a transcript is computed once
from one snapshot — so it cannot observe a write a preempting handler
makes to memory it later reads. The epilogue reads `$DA`, the rerun
request such a handler sets, and the walk's own `STZ $DA` at `$FC30`
would make that read always zero, so the handler would never take its
`JMP $FC03` chain exit into the sequencer. The walk therefore stops at
the two epilogue heads `$FC7C` and `$FD70`, plus `$FC8C` for a
reentrant interrupt that bails without touching a channel, and leaves
the epilogue emulated so that read stays live.

The other is `CLI` itself. The core samples the interrupt on an
instruction's last cycle, and `OP_CLEARF` runs that sample before it
clears the flag, so the instruction after a `CLI` still runs masked. A
checkpoint that published the post-`CLI` status opened the window one
instruction early and a nested timer interrupt arrived nine master
cycles ahead of the machine. The `CLI` checkpoint must publish the old
mask and let the clear land on the next one.

Hooked on its own the driver is admitted at every entry — 254,434 of
254,434. With the whole registry deployed it is admitted 118,904 times
of 254,990, 46.6%. The rest arrive while another checkpointed transcript
is suspended, and the core does not consult the replacement hook while
one is active, so those run emulated. That is the single largest
remaining lever on the percentage: 105,386,211 cycles are blocked by
the no-nesting rule rather than by anything unported. It is a limit of
the hybrid harness, not of the port, and it disappears with the
emulator rather than before it.

That figure moves the wrong way as the port grows, and the palette
slice below is the first place it showed. A long transcript shadows the
driver for its whole body: `00:E9B6` runs 9,745 cycles, spans about two
timer periods, and the interrupts that land inside it cannot reach the
driver's hook. Making the three palette leaves native added 9,937,182
cycles and gave back 694,000 of them in driver entries — 1,181 fewer
than before. Net it is still strongly positive, but the arithmetic is
worth stating: the longer the transcripts get, the more of the driver
the no-nesting rule swallows.

The exception is worth as much as the rule. `00:EB30`, added in the
same area a slice later, runs up to 18,585 cycles — more than three
timer periods — and cost the driver nothing at all: not one entry, not
one cycle. Every one of its 3,599 calls arrives with `I` already set,
because the upload has to land inside the blanking interval, so no
timer interrupt was ever going to be delivered inside it. Body length
is only half the question; whether the routine runs masked is the
other half, and it is one `--observe-hook` run to find out.

The wrapper slice below then settled what the cost actually scales with,
and it is not per-call length. Its nine transcripts are 36 to 162 cycles
each — a fortieth of `00:E9B6` — and there are 52,911 of them, 4,849,479
cycles of native time in total. They cost the driver 1,326 entries and
756,342 cycles, 15.6% of the slice's own gross, which was the largest
shadowing bill any slice had paid at the time. Total
native time is the quantity that sets the scale, not per-call length: a
thousand small transcripts shadow the driver exactly as well as one large
one. The split inside the slice is the proof: its three masked wrappers run
inside the VBlank handler and cost nothing at all, and the whole bill comes
from the six that run on the main thread.

## The music sequencer

Bank `45` is the other half of the audio path. The timer driver streams
samples; the sequencer decides what they are, walking its voices once per
frame from `45:4015`, programming the PSG register file and maintaining
the per-voice records in `$2E00`-`$2FFF`.

Unlike the driver it is not flat: the tick calls sixteen subroutines, so
the port is incremental rather than one transcript. Ten of them are now
native — the sample/envelope group the voice walk calls once per voice per
frame, the register programmer that pushes the result out, and the two
routines that decide what the notes are in the first place:

| Entry | Admitted | What it does |
| --- | ---: | --- |
| `45:48B4` | 72 of 72 | Sequence-data fetch, the shared command decoder |
| `45:4883` | 22,664 of 22,664 | Pitch/period update (inlines `48B4`) |
| `45:48F6` | 22,664 of 22,664 | Sweep accumulator update (inlines `48B4`) |
| `45:49A2` | 22,664 of 22,664 | Vibrato accumulator update |
| `45:49B6` | 3,604 of 3,604 | Voice-latch clear |
| `45:49F9` | 22,622 of 22,664 | Voice commit, which drives `$0800`/`$0804` |
| `45:4211` | 7,198 of 7,198 | The two pending-event gates |
| `45:4228` | 1,142 of 1,142 | Portamento stepper |
| `45:457A` | 2,219 of 2,299 | Command interpreter |
| `45:4142` | 1,792 of 3,604 | PSG register programmer, six voices plus the LFO |

One walk serves all ten. Each stops in front of its own `RTS` and hands
the return back to the core, and any call the walk makes on the way is
inlined into the same transcript — which is why `48B4` is admitted only
72 times on its own: the other 25,896 calls to it are made from inside a
`4883` or `48F6` transcript and never reach the hook. `457A` inlines four
callees the same way: the `$42BA` dispatch trampoline at `4569`, the
balance ramp `4522`, the note-to-period conversion `46D7`, and the forty
command handlers themselves.

Three rows are partial, for two different reasons.

`$F5`, `$F7` and `$F9` are the timer driver's per-channel bank bytes, and
they are the only bytes in this bank's working set that another thread of
control writes: the driver sets one when it maps a channel's data bank and
clears it when the channel falls idle. `4142` reads all three, `49F9`
reaches them through `$20F5,Y`, and a transcript reads them from a snapshot
taken before it runs. The walk therefore declines unless the interrupt mask
is already set at entry — `4142` brackets each voice in PHP/SEI/PLP, so a
masked entry stays masked for the whole body — or the body finishes before
the next serviceable timer interrupt. That is a correctness boundary, not a
horizon heuristic: without it the transcript would act on a value the driver
had already changed.

`457A` declines for a different reason: 45 of its calls hit the `$82`/`$92`
command, whose handler pops four bytes off the stack and jumps to `$40EE`,
abandoning the routine's own frame. A transcript that has to stop in front
of an `RTS` cannot express that. The other 35 are command handlers the
census route never reaches, left untranscribed rather than written blind.
Both would go away if `45:4015` were ported, because at that level the
escape is ordinary internal control flow — but it cannot be, for the
reason below.

Verification goes past the state census here, and it earned its keep twice.
The census is the direct oracle for an audio port, because it hashes the
audio, and it is unchanged. On top of that the regression compares three
artifacts against a pure-assembly run of the same route: 5,458,568 work-RAM
writes covering every voice record, the zero-page command pointer, the
timer driver's per-channel state and the stack, 699,251 PSG and timer
writes, and the census itself. All three are byte-identical, so the writes
match in value, address, order and master-cycle offset, not merely in end
state.

The stack range is the load-bearing part, and it has now caught two faults
the census could not. `JSR` pushes the return address *before* `ADDCYC(6)`,
while every other store in the walk lands on its instruction's final cycle,
so the first slice credited two stack writes 21 cycles late; widening the
work-RAM range to cover `$21E0`-`$21FF` found it on frame 148 of 3,600.
The third slice's `PLP` at `46AE` then published the caller's flags at its
checkpoint, so an interrupt landing on that exact instruction pushed the
pre-pop status — two differing bytes in 5.5 million, both on the stack,
with the census matching either way because the handler restores `P` on the
way out.

The bank is now 25,029,471 of 45,586,602 cycles native, 55%, and that is
where it stops while the emulator is still here. The remaining 20,557,131
are the per-frame tick at `45:4015`, which calls everything above, plus
`45:4936` and the track loader `45:4BCC`.

`45:4015` is not merely unwritten: the snapshot rule forbids it. Its
voice loop reaches `45:4148`, `LDA $F5,X`, three times per call, so any
transcript for the tick reads driver state and has to finish before the
next serviceable timer interrupt. The tick's body is 12,667 master
cycles and the timer period on this route is 5,068, so it never can. The
same rule that admits `4142` at half its calls — 2,054-cycle body, same
5,068-cycle period — rejects the tick at all of them. Porting it would
have produced a transcript builder that declines 3,599 times out of
3,599, which is why the effort went to the palette instead.

This is the second thing on the list that is blocked by the hybrid rather
than unported, and it has the same resolution as the first: with native
time and interrupts there is no snapshot, so there is nothing to go
stale.

## The palette shadow buffer

Gameplay code never writes the VCE. It keeps thirty-two 32-byte blocks of
packed nine-bit GRB in a shadow buffer at `$27B9`-`$2BB8`, marks the blocks
it changed in `$2CCC`-`$2CEB`, and `00:EB30` pushes the dirty ones out to
the VCE ports once a frame. Four routines are now native, and they are
the port's first move into the video paths:

| Address | What it is | Native calls | Master cycles |
| --- | --- | ---: | ---: |
| `00:EB30` | The upload: dirty blocks out to the VCE | 3,152 of 3,181 | 6,870,516 |
| `00:E9B6` | Block interpolator: one crossfade step over sixteen colours | 672 | 6,548,946 |
| `00:EBA5` | Block stager: a 32-byte copy plus the dirty flags | 1,121 | 2,629,866 |
| `00:E93C` | The sixteen-bit compare the fade drivers branch on | 8,969 | 758,370 |

The bottom three are admitted on every call, which is unusual enough to
explain. They are leaves — no `JSR`, no device port, and nothing another
thread of control writes — so there is no horizon to miss and no snapshot
to go stale. An interrupt landing inside one is handled the way it always
is, by a checkpoint.

The interpolator is the interesting one. Each colour's three channels are
summed and compared against the step counter at `$2CEC`; colours whose
total falls below it are skipped, which is what staggers the fade, and the
rest have exactly one channel nudged a step toward the target — whichever
of the three differences is largest. The differences are computed with
`SBC` and no clamp, so a channel the shadow has overshot wraps to a large
unsigned value and is treated as furthest away, which is what drives it
back.

`00:EB30` is the first routine in the project to drive a device other
than the VDC and the PSG. It walks the thirty-two dirty flags, and for
each block it points the colour table at `$0402`/`$0403` and pushes
sixteen colours through `$0404`/`$0405`. Twenty-nine of its 3,599 calls
take a second arm instead, where a single `TIA $27B9, $0404, $0400`
moves all 1,024 bytes at once; that is 1,024 writes against a channel
that carries 512, so the walk declines in front of the first store
rather than truncating the upload. A further 418 calls never reach the
hook because another transcript is suspended when they arrive.

Admitting it took a two-line widening on each side of the boundary: the
VCE register file was added to the replacement write channel's
allowlist, and to the core's wait-state compensation. The second is
what makes the timing come out. `IOWrite` steals a CPU cycle for both
the VDC ports and the VCE, and the interruptible path already advanced
to the cycle *before* a VDC write so that steal landed inside the
declared offset; the VCE was outside that test, so the first run of the
transcript ran three master cycles long per colour — 102 per block,
accumulating all frame. The write values and their order were already
right at that point. Only the clock was wrong, which is exactly the
class of fault a value-only comparison would have passed.

Three neighbours stay emulated. `00:EAA7`, the fade-to-black stepper,
is 205,012 master cycles per call — roughly nine times the checkpoint
cap, so it cannot be a transcript at any length. `00:E94D` and
`00:EA77`, the two fade drivers, both call the frame-sync spin at
`00:E321`, so a transcript for either would have to span twenty-one
frames.

Verification is the two-run diff, now over three artifacts: 7,369,685
work-RAM writes covering the shadow buffer, the dirty flags, the
zero-page scratch and the stack; 115,688 VCE register writes; and the
state census. All three are byte-identical to a pure-assembly run of the
same route. Nothing in this slice pushes, so every stack write in that
trace belongs to surrounding code — which is exactly what makes it a
good check on the cycle counts.

## The bank-switching call wrappers

Every cross-bank call in the game goes through one of five small wrappers.
The caller leaves a physical bank in `$30` and an entry offset in `$2F`; a
wrapper maps the bank into an MPR slot, jumps through the callee's `$40xx`
table, and unmaps it on the way out. `$1E`, `$1F`, `$20` and `$21` are the
zero-page shadows of MPR2 through MPR5, and keeping the shadow and the
register in step is what makes the idiom re-entrant: a wrapper that
preempts another restores both from its own stack frame.

Nine entry points are native, admitted on every one of 52,911 calls:

| Address | What it is | Native calls | Master cycles |
| --- | --- | ---: | ---: |
| `00:E241` | Banked call, prologue: save MPR2/MPR3 and map `$30` | 11,599 | 1,322,286 |
| `00:E255` | Banked call, epilogue: take the result, restore MPR2/MPR3 | 11,599 | 1,043,910 |
| `00:E262` | The trampoline: build `$40xx` in `$2CBE`/`$2CBF` | 11,671 | 700,260 |
| `00:ECC6` | The VBlank handler's music call: map banks `$45`-`$47` | 3,503 | 567,486 |
| `00:E219` | Map the fixed bank pair for the mode at `$55` | 3,523 | 422,760 |
| `00:ECE2` | Restore MPR2-MPR4 after it | 3,503 | 409,851 |
| `00:E20D` | Map `$30` into MPR4/MPR5 | 1,861 | 133,992 |
| `00:ECF2` | Point `$47`/`$48` at `$4003` and enter the sequencer | 3,503 | 126,108 |
| `00:E200` | The asset resolver's tail | 1,861 | 122,826 |

Four of those are heads and five are the addresses a wrapper's call comes
back to, because a wrapper exists to call something and the transcript has
to stop in front of that call. Two of the stops are indirect jumps,
`00:E26E` and `00:ECFA`, and the walk stops in front of both rather than
resolving them: each reads a vector the same transcript just wrote, so
handing the jump back to the core costs six instructions of coverage and
removes the only place this module would have to compute a resume bank.

This is the first slice whose transcripts change the bank mapping. `TAM`
is expressible because `CpuRegisters` carries all eight `MPR` slots and a
checkpoint applies them, so the only real question was whether anything
here reads state an interrupt handler leaves changed. Nothing does. The
VBlank handler's own wrapper at `00:ECC6` is the sole interrupt-context
writer of `$1E`-`$21` in the whole game, and it restores all three from
the stack before it returns; the timer driver never touches them. That was
settled from a work-RAM write trace of the four addresses before any code
was written — the same two-query screen that ruled out `45:4015`.

Verification is the two-run diff over 6,389,776 work-RAM writes and the
state census, both byte-identical to a pure-assembly run of the same route.
The whole stack page is in scope rather than a window of it: this family is
nothing but stack-balanced save and restore, and its pushes land wherever
the caller left `S`, spanning `$21E2` through `$21FD` on this route.

`00:ED5E` is the fifth wrapper and is deliberately absent. It is entered
with two of its four stack slots already pushed by its caller, so its entry
contract belongs to the caller rather than the routine, and it is 23,000
master cycles across 72 calls — 0.4% of this family.

## The VDC interrupt handler

`00:E058` is the display interrupt. It reads the VDC status register at
`$0000` into `$01` and dispatches on it: the VBlank bit sends it to
`00:E0EB`, everything else to `00:E136`. The head is not portable — its
whole decision is a byte from a device register, and a replacement
callback receives work RAM and registers only — but nothing downstream of
that read needs the device again, so the bodies are.

Six entry points are native. Hooked on their own they are admitted on
every one of 13,932 calls; the counts below are from the deployed
registry, where the interrupt sometimes arrives while a main-thread
transcript is suspended and the handler runs emulated for the same
no-nesting reason the sound driver does:

| Address | What it is | Native calls | Master cycles |
| --- | --- | ---: | ---: |
| `00:E0EB` | VBlank prologue: program VDC `$08`/`$07`/`$05` from the RAM shadows | 2,311 of 2,748 | 457,578 |
| `00:E123` | Epilogue after the music call: restore MPR6 and unwind | 3,132 of 3,212 | 328,860 |
| `00:E136` | Non-VBlank arm: reprogram the split, tick `$222A` | 1,313 of 3,599 | 303,750 |
| `00:E117` | Bump the frame counter at `$00`, take or skip the music call | 3,162 of 3,599 | 182,304 |
| `00:E183` | Secondary handler's epilogue | 351 of 387 | 43,173 |
| `00:E179` | Secondary handler's prologue | 351 of 387 | 20,007 |

Every walk stops one instruction short of its `RTI`, in front of the `PLP`
that restores the interrupted status byte, and that is the whole lesson of
the slice. The core samples the IRQ at `LastCycle`, which for `PLP` runs
*before* the pop; a checkpoint carries one register set and samples with
it, so a transcript covering `PLP` samples with the restored mask instead
of the one the instruction ran under. Assembly services a timer interrupt
between that `PLP` and the `RTI`; the first draft of this slice swallowed
it, and the state census caught it. This is the same fault the sound
driver's `CLI` produced from the other direction, and the general rule is
now stated once: an instruction that changes `I` cannot be summarised by a
checkpoint that publishes its result.

That mattered because the handler does not run masked throughout, which
is not obvious: an interrupt sequence sets `I`, and nothing in the handler
clears it. Bank `45` does. Three of its critical sections end with an
unconditional `CLI` rather than restoring the caller's mask — `45:4872`,
`45:49F2` and `45:47EE`, 376 executions between them — so the music tick
below `00:ECC6` hands the handler back with interrupts enabled. Counting
interrupt entries in an assembly write trace of the stack page puts 78 of
them inside these six walks, every one at or after `00:E123` and none
before a `JSR $ECC6`.

The shadowing bill is small in spite of that: 64 driver entries and
36,330 cycles, 2.7% of the slice's own 1,350,720, because the unmasked
stretch is the short one.

Verification is the two-run diff against pure assembly over three
artifacts: 4,989,037 work-RAM writes including the whole stack page,
2,036,234 writes to the VDC's three base ports censused directly with
`--bus-write-range`, and the state census. The stack page is what makes
the interrupt fault visible at all, because a swallowed interrupt moves
where its handler pushes.

## The graphics upload paths

`00:E3C0`–`E47C` is one idiom three times over: point a VDC or VCE write
pointer at a base address, then push words through the data ports until a
counter runs out. Nothing in the region reads a device register, so unlike
the interrupt dispatcher above it is portable end to end.

| Address | What it is | Native calls | Master cycles |
| --- | --- | ---: | ---: |
| `00:E439` | Stream-record loop: the decoder's continuations | 326 of 326 | 5,883,540 |
| `00:E41F` | The generic word-stream decoder's head | 41 of 41 | 813,204 |
| `00:E403` | VCE colour-table clear loop | 16 of 16 | 128,136 |
| `00:E3FC` | VCE colour-table clear | 4 of 4 | 37,704 |
| `00:E3D7` | VRAM clear loop | 4 of 4 | 25,524 |
| `00:E3C0` | Clear 512 VRAM words from `$7800` | 2 of 2 | 20,736 |

The decoder is the whole prize, and it is the first thing in the port that
does not fit in a transcript. One call is 167,000 master cycles, 3,400 port
writes and 12,400 instructions, against a channel of 512 writes and 2,048
checkpoints. So it chunks. Each routine has two entry points — its head, and
the head of the loop — and a transcript ends in front of the backward branch
that closes the loop. The core executes that branch, lands on the loop head,
and calls the replacement again for the next chunk. Nothing in the core
changed to allow this: the hook already fires on any fetch at a registered
address, and the replacement contract already ends by handing one instruction
back. The 41 decoder calls become 41 head transcripts and 326 continuations,
and the leak is the branch itself — eighteen master cycles a chunk, 5,868 on
the route.

Where to chunk is a budget decision, not a fixed count. `00:E479` reads the
next stream record's command byte before committing to it and stops if that
record would not fit in what is left of either channel, so a transcript never
abandons work it has already transcribed. A record is at most 127 words on
this route — 258 writes — so the first record of a chunk always fits and the
walk always makes progress. That is the property that matters: a chunk that
made no progress would loop for ever.

The other precondition was shared state. `$2F`/`$30` is the game's
general-purpose source pointer, written from some 340 sites across eight
banks, and a transcript that reads it is only sound if nothing writes it
underneath. That was measured rather than argued: bracketing each of the 41
calls between its header's `$06` store at `00:E422` and its last data-port
write, all 23,300 writes to `$2D`-`$30`, `$37` and `$38` inside those windows
come from the decoder itself, and none from interrupt context.

The shadowing bill runs the other way here. The VDC handler's transcripts
shadowed the sound driver from inside interrupt context; these are main-thread
transcripts averaging 18,000 cycles, more than three timer periods, so the
interrupts that land inside them cannot reach their own hooks. 6,908,844
native cycles cost 317,196 elsewhere across 956 entries — 130,122 in the sound
driver, 165,123 in the music sequencer, 21,348 in the VDC handler and its
bank wrapper, 603 in the palette upload. Net `+6,591,648`. At 4.6% of gross
that sits between the bank wrappers' 15.6% and the VDC handler's 2.7%, and
it is the cheapest bill any main-thread slice has paid.

One of the 367 transcripts is abandoned partway through a repeat record and
the assembly finishes it: 45 loop iterations and one record tail out of
6.9M cycles. That is the core's checkpoint guard doing its job — it resumes a
suspended transcript only when the program counter, stack pointer, registers
and all eight MPR slots match what the checkpoint published, and otherwise
drops it and lets the assembly run. The fallback is by design and the census
is unaffected.

Verification is the two-run diff against pure assembly over three artifacts:
6,036,242 work-RAM writes covering the decoder's shared zero page and the
whole stack page, 2,151,922 writes to the VDC and VCE register files censused
directly with `--bus-write-range`, and the state census.

## The tilemap upload, and an instruction a checkpoint cannot express

`00:F261`–`F4F1` is the other half of the graphics driver's port work and
the last coherent video row in the inventory. Where `00:E41F` streams a
prepared word list into VRAM, this decides which row of the scrolling
table has just come into view and pushes it. It is two routines:
`00:F3E7`, which programs a VRAM address into the VDC and writes 32 words
— each a tile index from an MPR-mapped source with an attribute nibble
from a work-RAM array folded in — and `00:F261`, which decides whether the
camera has crossed a tile boundary, resolves the source through the
already-native bank helper at `00:E1FD`, calls the writer once or twice,
and folds the movement back into the camera.

Nothing in the region reads a device register, so the whole 5.7M row was
phase-1 work. Ten entry points, every one admitted on every call:

Six of those entries are ordinary: a transcript stops in front of a call,
so each of the driver's six `JSR`s needs its return address registered.
Two of them land on `00:E20D` and `00:E200`, native since the wrapper
slice, so stopping there re-enters that module instead of transcribing
the same eleven instructions again.

`00:F426` and `00:F42A` are the finding. Every other instruction in the
region charges its cycles in one `ADDCYC` and one `LastCycle`, which is
exactly the shape a checkpoint expresses: advance to the sample, sample,
advance to the end. `BBR` is not one instruction in the core, it is two
macros — `LD_ZP` reads `$27` and samples, then `JR` branches and samples
again — so the machine crosses `00:F423` in four clock steps where a
checkpoint crosses it in two. The interrupt outcome at the boundary is the
same either way, but the steps are where the core tests `next_event`, and
a coarser step runs the video `EventHandler` at a later timestamp. That
shifted a VDC event, which moved a timer interrupt one instruction early
four times in 3,600 frames — twice inside the walk, and twice in assembly
*downstream* of it, which is what made it clear the perturbation outlives
the transcript.

The fix is to hand `00:F423` back to the core and register the two
addresses the branch arrives at, which is why the loop has 17,248 entries
instead of 539. Splitting the difference is not available: an extra
checkpoint inside the `BBR` would make that boundary an extra interrupt
opportunity the machine does not have. It costs 365,664 master cycles, 77%
of everything still emulated in the region.

Shared state was measured before the walk was written, and by call windows
from a `00:F261` observer rather than inferred from the writes — the
previous slice's bracketing trick does not work here, because parts of the
region are also reached independently. Across all 2,649 calls, 92,978
writes inside those windows are the routine's own; the only others are
8,118 interrupt-frame pushes below the live stack pointer and four stores
to `$20`, an address the region writes only inside the `00:E1FD` it stops
in front of and never reads.

The shadowing bill was the largest any slice had paid, in proportion and
in absolute terms: 5,180,931 native cycles cost 937,827 elsewhere across
1,717 entries, 923,088 of it the sound driver's. Net `+4,243,104`. At
18.1% of gross it beats the bank wrappers' 15.6% on a fifth less native
time, which refines the rule the wrapper slice drew rather than confirming

the transcript. A driver entry that lands inside one runs emulated while
the transcript stays suspended, so its 563 cycles are shadowed too, and
anything arriving inside *those* is shadowed in turn.

artifacts: 6,977,084 work-RAM writes covering the driver's shared zero
page and the whole stack page, 2,036,234 VDC register writes censused with
`--bus-write-range`, and the state census.

## Composition, and what a longer transcript costs the driver

The sweep at `01:CB48` no longer stops in front of `JSR $CC1A`. It
transcribes the call, splices the scanner's own transcript in where the core
would have run it, transcribes the `RTS`, and hands control back at `01:CB61`
with the scan already answered. Nothing about the scanner changed: the same
`replace_collision_scan_vertical_reject` runs, on a staged work RAM that
carries the sweep's own writes, and its checkpoints and writes are shifted by
the cycle the call landed on. It is the pattern `01:CC1A` already used for
`01:CCD5`, applied one level up.

83,905 of the scanner's 85,715 calls compose. The 1,810 that do not are the
hit path, which leaves the scanner from the middle of itself at `CCD2` or
`CCD4`; there is no `RTS` to transcribe from there, so the walk rolls its
attempt back and ends in front of the call exactly as before. `01:CC1A` stays
installed for them.

The call boundary is gone. `01:CB5E` falls from 1,795,419 master cycles to
17,622 and `01:CC40` from 1,797,309 to 19,776; what is left is the hit path
and a few interrupt re-entries. `01:CB48` absorbs the scanner and becomes the
largest single native address on the route at 7.96% of all master cycles,
ahead of the sprite emitter.

The gross gain is exactly what the tax predicted — 83,905 × 42 = 3,524,010 —
and this is the one case where predicting it was safe, because a `JSR` and an
`RTS` cost 21 each whatever surrounds them. The bill was not safe to predict.
A composed walk is a longer transcript, and a longer transcript shadows the
timer driver for more of its length: `00:FC00` loses 1,184 admitted entries
and 683,271 native cycles, and sixteen other routines lose 11,790 between
them. 695,061 in total, 19.7% of gross, against the collision frame's 21.0%.
Net `+2,828,949`.

So composition pays for itself roughly four times over here, and it is worth
being clear about which half of that is transferable. The 42 cycles are
structural and will be there at every call boundary in the port. The
four-to-one ratio is not: it holds because this call sits in a loop whose
body is short, so the tax was a large share of the region. A call around a
long body is worth composing for other reasons, but not for this one.

## The Sorcerer tick, and a bill that is starting to look like a constant

`02:586F`-`02:5903` is the Sorcerer's per-frame tick: the largest block of
unported gameplay left on the route, and the only block of its size with no
native entry anywhere inside it. Its deployment and staging heads at `02:57F8`
and `02:5808` were already native; this is the three states that follow, for
the eight Sorcerers in slots `$17`-`$1E`. One routine in three pieces, split by
the two calls it makes to the collision-table interpreter at `03:6966`: the
staggered deployment delay on the sixteen-bit countdown in `$3B00,X`/`$3B80,X`,
the arrival state that reseeds the table cursors when the interpreter reports
its terminator, and orbit -- where all eight sit for the rest of the route --
which reads a four-entry difficulty table out of the bank's own ROM page and
copies the interpreter's event record from `$3A80,X` to `$3980,X`.

Five entry points, admitted on every call, 3,156,294 cycles gross across
41,144 entries and `+2,595,360` net.

| --- | --- | ---: | ---: |
| `02:58C2` | Orbit, to the interpreter call | 18,152 of 18,152 | 1,929,864 |
| `02:58DD` | Its return, to the final `RTS` | 18,152 of 18,152 | 1,034,664 |
| `02:586F` | Deployment delay | 1,240 of 1,240 | 103,854 |

Screening was the sharpest result the in-window ranking has produced.
Ninety-nine instructions across seven banks write the addresses this family
reads. Exactly **one** of them ever writes inside one of the family's call
windows -- `03:69D9`, the interpreter's own event store, which is this
family's callee -- and the other ninety-eight land inside a window on 0.0%
of their executions. Not "close to zero": zero.

The region is 4,055,142 cycles down to 910,530, and about 87% of what
remains is the same call tax the collision frame ran into: two `JSR`s to the
interpreter, two to the bank-01 wrapper at `$C018`, and three `RTS`
instructions. The interpreter is a candidate for composition, but unlike
`01:CC1A` it is an atomic body rather than a checkpointed transcript and it
already declines 2,850 of its own 34,259 entries at an interrupt horizon, so
splicing it into a longer parent would put a long uncheckpointed stretch
inside the walk. That is its own slice, and probably its own decision.

The shadowing bill was 560,934, 17.8% of gross -- the lowest of the last
four slices, and low enough to say something about the mechanism. Four
measurements now exist: 18.1%, 21.0%, 19.7% and 17.8%. Underneath them the
per-event numbers are almost identical. The driver costs 574 to 577 native
cycles per displaced entry every time, and one entry is displaced for every
2,900 to 3,300 master cycles a transcript holds the core. So the bill is
close to `gross / 3,000 × 575`, which is about 19%, and the spread between
slices is small next to that.

Two caveats before using it as a rule. It is an estimate of the *scale*, and
the four points span three percentage points either side, which is 100,000
cycles on a slice this size. And it is 1.7 times the naive figure: the timer
fires every 5,068 master cycles, so a transcript covering N cycles should
overlap N/5,068 of them, not N/3,000. That excess is measured, consistent
across three slices, and not yet explained. Keep measuring the bill with a
`--registry-exclude` run; the rule is for deciding whether a region is worth
starting, not for reporting what it delivered.

## What is left

Everything except the idle spin loop is now a porting target, because
the goal is a runtime with no emulator in it at all — video and audio
included. Earlier reports quoted a narrower "portable pool" that
excluded the graphics drivers; that distinction no longer means
anything and the figure has been dropped rather than carried forward
unverified.

Set the idle spin loop aside and 707,613,360 cycles are the machine
working; 530,161,950 of them, 74.9%, now run natively. The 177,451,410
still emulated are three blocks:

| Still emulated outside the spin loop | Master cycles |
| --- | ---: |
| Sound-driver entries the no-nesting rule blocks | 105,386,211 |
| Music sequencer's tick, blocked by the snapshot rule (bank `45`) | 20,647,350 |
| Remaining video-bank and gameplay code | 51,417,849 |

Only the third is unported code. The first is the half of driver entries
that arrive while another checkpointed transcript is suspended, which the
core runs emulated because it will not nest a replacement. The second is
the sequencer's per-frame tick, which the snapshot rule rejects at every
call for the reason given above. Both are limits of the hybrid harness,
both are measured here rather than estimated, and both disappear with the
emulator instead of before it — so 126,033,561 of the 177,451,410 is not
work anyone can do now.

The third is spread thin: no single address in it is worth more than
0.14% of the machine. The largest coherent groups left are the pad
reader `00:E195` (6.9M), the interpreter tail at `03:694A`-`6A37` (5.3M),
the palette shadow buffer at `00:E94C`-`EBD6` (3.8M), and the sequencer's
note handlers at `45:4517`-`4A9B` (3.2M).

The pad reader is in that list for form's sake. `00:E195` strobes the
joypad port at `$1000` and then *reads it back*, five times a frame, and a
replacement callback receives work RAM and registers — nothing else. No
amount of widening the write channel reaches it, which is what the plan
for this region assumed would be enough. The same is true of the VDC
interrupt handler's head at `00:E058`, whose first act is to read the VDC
status register. A routine that reads a device register cannot be a
transcript at all until that device has a native model, so both are phase
2 work rather than phase 1. Everything downstream of that read is now
native; see the section above.

Note that this percentage tracks only one of the three axes that
removing the emulator needs: which code executes natively. It does not
track device state or time. A native routine today still writes into
Beetle's PSG and VDC and runs on Beetle's clock, so the figure will
plateau well short of "the emulator is removable". See
[EMULATOR_ELIMINATION.md](EMULATOR_ELIMINATION.md) for the phases the
percentage does not cover, and for why the replacement no-nesting rule
is deliberately left unfixed.
