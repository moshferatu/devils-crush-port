# Native Fallback Hotspots

This document records measured, scoped profiling results used to choose the
next native-port batch. It is deliberately not a statement of whole-game
native coverage: the runtime captures bounded call scopes only for explicit
observer addresses.

The first profile uses the natural 3,600-frame matching-arrow route. It
observes the current collision parent, both new post-audio continuations, and
the scheduled `$4AEB` animation continuation. The run has 1,676 observed

The weighted cost is total master cycles plus 12 per ordered work-RAM write.
Cycle cost remains the primary payoff signal; the small write premium favours
routines whose port also removes a larger fidelity/testing burden.

natively for all 506 naturally observed countdown and phase-advance calls;
the 60/96-cycle branch transcripts and interrupt-bearing invocations remain
byte-identical. Its appearance-six scene-transition branch at `$4B00` was not
exercised by this route and remains assembly fallback, so the feature family
is not yet wholly native.

## Fixed-marker scope screen

The fixed-marker family was next profiled with native parent/controller
adapters enabled and the common drawing submission `01:C05D` observed. Its
1,119 calls consumed 3,348,582 master cycles and emitted 59,978 ordered
work-RAM writes (weighted cost 4,068,318). That is a useful measurement, but
not a native-gameplay candidate: `C05D` is the shared ROM video-drawing jump
table and the plan deliberately retains original graphics drivers in the
emulated compatibility layer. The profile therefore records an explicit scope
rejection rather than treating raw cycle count as automatic port priority.

## Spider parent composition re-screen

A Release follow-up observed both parents with their current native children
enabled. The state census remains byte-identical to the assembly baseline:
`03:6966@all` admits 51,294 of 54,149 calls and `03:65A4@all` admits all
5,441 calls. The two outer controllers still account for 4,790 direct calls
and 4,790 naturally scheduled collision-table entries, so their raw cost is
substantial but not independent of the shared interpreter.

The short no-hit wrappers were screened as a composed candidate and rejected
for now. `03:6966`'s admitted transcript depends on the precise nested entry
time and interrupt horizon; a parent wrapper must reproduce that temporal
context as well as the selector, two stack frames, and appearance call. A
simple adapter did not preserve the frame-873 state census, so it was
discarded rather than widening native coverage with an inexact composition.
Keep both parents assembly-backed until a nested-call timing adapter is
proven by an original parent transcript.

**Superseded, and the reason is worth reading before trusting the paragraph
above.** That rejection is correct about the replacement it was written against
and wrong about the routine. `03:6966` was an atomic body then, so its result
did depend on the entry time and the interrupt horizon, and a parent could not
reproduce that. It is an instruction-boundary transcript now: it admits 54,149
of 54,149 calls, it declines nothing at a horizon, and a parent that splices it
does not have to reproduce any temporal context at all, because the child emits
the same checkpoints and the same writes wherever it is called from. The
Sorcerer tick composes it at two sites and the consumer at `03:7F57` at one, all
three verified against assembly. The "nested-call timing adapter" this section
asks for turned out not to be a thing that needs building.

**Re-screened.** Nothing in the recorded objection survives, and the parents are
smaller than the table above makes them look. Each is nine instructions:

```
6490  LDA #$2A        651F  LDA #$2C
6492  LDY $3C80,X     6521  LDY $3C80,X
6495  BEQ $6499       6524  BEQ $6528
6497  LDA #$2B        6526  LDA #$2D
6499  JSR $6966       6528  JSR $6966
649C  JSR $65A4       652B  JSR $65A4
649F  LDA $3800,X     652E  LDA $3800,X
64A2  BMI $64A5       6531  BMI $6534
64A4  RTS             6533  RTS
```

Both children are 100% transcripts on the route — `03:6966` admits 14,307 of
14,307 with zero horizon declines and `03:65A4` all 5,441 — so there is no
temporal context to reproduce and the splice is the one the Sorcerer tick
already performs, twice. Front's `BMI` tail at `64A5` is taken 3 times in
3,600 frames and can simply end the walk; Side's at `6534` is never taken.

What the re-screen also establishes is that the prize is small. The 1.85M and
1.97M in the table are inclusive of the children, which are already native.
The parents' own bodies are 312,084 and 330,060 master cycles, 642,144
together, **0.05% of the route**, and the two `RTS` instructions handed back
take about 115,000 of that off again. There is no caller to compose them into
either: the addresses `$6490` and `$651F` do not occur anywhere in the 384KB
ROM image, so both are reached by computed dispatch and porting them removes
no call boundary above.

So the objection is dead and the slice is worth roughly 0.04% net. Priced, not
deferred: it is available whenever completeness matters more than share, which
is the position the port ends in.

modelled V because nothing downstream read it, but a checkpoint pushes P onto
the stack when an interrupt lands.

## The two loops' linkage, and stack traffic as a target

The following pass re-ranked the same way and found that the top five entries
that are neither the spin loop nor the sound driver were all linkage — calls,
returns, and the branch that resolves a call's result:

| Routine | Cycles still emulated | What it is |
| --- | ---: | --- |
| `01:C51E` | 4,158,384 | `BSR $C52C` into the dispatch half |
| `01:C520` | 3,637,518 | `JSR $C606` into the queue filer |
| `01:C654` | 3,639,030 | the queue filer's `RTS` |
| `01:CB6B` | 4,105,008 | the collision sweep's `INC`/`DEC`/`BNE` tail |
| `01:CB61` | 1,029,657 | `BCC` on the vertical scan's result |

The last two are the collision sweep's version of what `01:C523` was for the
actor loop, and they were found the same way. The `01:CB48` walk absorbs the
tail for every slot it rejects, but a slot that reaches the vertical scan at
`01:CC1A` leaves the transaction there, so the branch and advance that follow
are separate arrivals. `01:CB6B` is hooked rather than `01:CB61` alone because
the hit path at `01:CB68` also falls into it; hooked on its own the advance
sees all 400,892 iterations.

The first three are the more interesting result, because the earlier note above
read the contract's "the RTS itself remains emulated, preserving stack and
caller-return behavior" as a prohibition. It is not one. `output_registers`
carries the stack pointer, the stack page is ordinary work RAM, and
`native_replacements_collision.cpp` had been modelling `JSR` frames for the
nested collision compositions all along. What the comment describes is the
convention for a *whole-routine* replacement, not a limit on what a transcript
may contain.

Pricing them needs three facts from `huc6280_ops.inc` and `huc6280.cpp`:

- `JSR` (`$20`) and `BSR` (`$44`) both `PUSH` twice **before** the first
  `ADDCYC`, so each stack byte carries the instruction's *start* offset, not
  its end. `RMW_ZP` writes after `LastCycle()`, so an `INC $64` carries its
  end offset. The two conventions differ and both are observable.
- `JSR` is 7 CPU cycles and `BSR` is 8 (`ADDCYC(4)` plus a taken `JR`), so 21
  and 24 master cycles. `RTS` is 7, and pops, so it writes nothing at all.
- `RMB`/`SMB` are 7 CPU cycles, not the 6 an ordinary zero-page read-modify-
  write costs: `RMW_ZP_B` adds a cycle that `RMW_ZP` does not.

Each of the three linkage transcripts is one instruction long, and `01:C654`
reads the frame under the stack pointer to confirm it is the one `01:C520`
pushed rather than assuming that any arrival at that `RTS` is this loop's.

The regression scopes its write range to `21FC-21FD`, the pair of stack bytes
the loop uses at its usual `$FD` stack pointer. That is deliberate: a
mismodelled push order, pushed value, or push timestamp shows up directly in
1,068,240 traced writes instead of only as downstream divergence. A wider
`21F0-21FF` trace over the same route also matches assembly exactly, at
3,722,042 writes, but is too large to keep as an artifact.

Together these took the registry from 28.22% to 29.49% of all master cycles,
and from 77.0% to 80.4% of the portable pool. The main actor loop and the
collision sweep are now native instruction for instruction.

## One walk, five entry points: the SAT submission driver

With both loops closed, the largest remaining entry outside the spin loop and
the sound driver was the satellite-attribute driver at `08:4036-40C2`, at
9,128,259 cycles. It had been rejected twice before, and for a real reason: it
calls `08:40DF` twenty-one times per frame at about 944 cycles each, so a
whole-routine transaction would have to subsume every one of them — far past
both the 512-write cap and any interrupt horizon.

The way through is to stop thinking of a replacement as covering a routine.
The hook fires at every instruction where no replacement is active, so the
addresses that matter are the ones control *arrives* at with the machine
between transactions. For this driver there are five: the head at `08:4036`,
and the four addresses a `JSR $40DF` returns to (`08:4063`, `08:4075`,
`08:4088`, `08:4097`). One shared walk starts at any of them and runs until it
reaches the next `JSR`, which the machine executes and which re-enters the
native emitter.

The walk is shared rather than five separate transcripts because the stopping
points chain. Draining one queue empty falls straight into the next, so an
arrival at `08:4063` can end anywhere from `08:4060` to `08:40C3`:

```
4036  point MAWR at $7800 + ($58 << 2), select VWR
4056  drain $2C3A/$2CBC downward           -> JSR $40DF at 4060
4068  drain $2BBA/$2CBA downward           -> JSR $40DF at 4072
407A  emit slot 0 when on camera, not hidden -> JSR $40DF at 4085
4088  drain $2BBA from $7F down to $2CBB   -> JSR $40DF at 4094
409B  re-point MAWR past the emitted entries, fall into 40C3
```

Four details shaped it:

- The walk re-reads two bytes it writes — each queue's cursor is decremented
  and then loaded again at the top of its loop — so those are shadowed rather
  than read from RAM that the transaction has not committed yet.
- `PHY` at `08:4093` charges its cycles before it pushes, so its write lands
  at the instruction's *end*, the opposite of the `JSR`/`BSR` convention
  established in the previous section. Both appear in this one routine.
- `$4E` reaching `$40` skips the tail clear. The route never produces one, so
  the walk stops at `08:40A6` and leaves the branch to assembly rather than
  running a transcript nothing has exercised.
- Entry counts change when the hooks are deployed together: `08:4088` is
  entered 3,492 times alone but 2,567 times alongside the others, because
  their walks reach it inline through the ball slot's two branches.

The regression scopes its trace to the driver's own work-RAM output — the port
shadow at `$2006`, the sprite count at `$204E`, and the two cursors at `$2CBA`
and `$2CBC` — 233,267 writes matching assembly exactly. Its VDC port writes
have no work-RAM trace, so the census carries them, and it hashes the rendered
framebuffer every frame.

This took the registry from 29.49% to **30.07%** of all master cycles. The SAT
path in bank `08` now runs natively from its first instruction to its last;
only the four `JSR $40DF` instructions and the closing `RTS` are left to the
machine. Everything still emulated outside the spin loop and the sound driver
is 21,582,381 cycles, 1.67% of the machine, and no single address in it is
worth more than 0.14%.

## The sound driver, and what a device-register port costs

The timer interrupt handler was the largest single block left outside the spin
loop, and the screening notes here had it wrong twice over. They filed it as
"timer IRQ and sound driver (`00:FC00`–`FDFF`, bank `45`)" and ruled it out
because it "drives the PSG through hardware-page registers at `$0800`/`$0806`
and re-maps banks with TAM/TMA between writes."

Bank `45` is not part of it. `$FC06` holds the table `48 49 4A 4B 4C 4D 4E 4F`,
so the driver's data banks are `48`-`4F`, mapped at `$C000` by `TAM #$40` and
only ever read. Bank `45` lives at `$4000`-`$4CB8` and is the music sequencer,
a separate component that programmes `$0801`-`$0809` directly. At the time of
this screen it was unported, and at 46,078,773 cycles it was the largest
emulated block outside the spin loop; the section below took the first slice
of it.

The handler itself runs `00:FC00`–`00:FE48` and is unusually tractable: a flat
state machine with **no subroutine calls at all**, three PSG channels walked at
X = 4, 2, 0, each streaming five-bit DDA samples through `$0806`. The bank
re-mapping was never an obstacle — `output_registers.mpr[]` and every
checkpoint carry the full `MPR` set, and the core applies them with `SetMPR`.

What it did cost was the write channel, which now carries the PSG file
`$0800`-`$0809`, the timer `$0C00`-`$0C01` and the interrupt controller
`$1402`-`$1403` alongside work RAM and the VDC ports, plus a
`--bus-write-range`/`--bus-write-trace` census channel, because device writes
never show up in a work-RAM trace. Both are in
[NATIVE_PORT_WORKFLOW.md](NATIVE_PORT_WORKFLOW.md).

Two screening lessons generalise:

- **Read the profile's per-address average before believing a total.** The
  region profiled at 249,675,363 cycles, but 72,383,913 of that sat on the two
  `RTI` instructions at 305 and 261 master cycles per execution against a real
  cost of 21. The profiler charges each address the span to the next
  instruction hook, and an `RTI` that returns into a suspended transcript is
  charged that transcript's unhooked remainder. The driver's true instruction
  time is 177,203,574. Every other address in it profiles at a clean 6, 12, 15,
  18 or 21, which is exactly how the artifact was found.
- **"It writes hardware registers" is a question, not a verdict.** The bounded
  answer — name the register file, confirm from the profile that its stores
  cost no wait cycles, and census them — took a 13.7% block of the machine that
  three earlier passes had written off.

## The music sequencer, and screening a bank instead of a family

Bank `45` was the largest emulated block outside the spin loop once the sound
driver landed. Screening it needed a different instrument from the usual
observer set, because the question was not "which of these siblings is the
next leaf" but "what shape is this bank".

The instrument was the whole-ROM instruction profile, read three ways:

1. **By bank.** `45` is 46,078,773 cycles over 1,078 executed addresses. The
   flatness is the finding: the hottest single address is 0.042% of the
   machine, so there is no inner loop to take and no point ranking addresses.
2. **By call target.** Scanning the executed addresses for `JSR`/`BSR` opcodes
   gives the bank's entire call graph in one pass — sixteen targets, twelve of
   them leaves. That converted an intimidating 1,078-address region into a
   sixteen-row table.
3. **By reachable set per target.** Walking control flow from each target
   without following calls attributes the bank's cycles to routines. The five
   routines the voice walk calls once per voice per frame hold 20.0M of the
   46.1M.

The first slice took the seven leaves of the sample/envelope group; the second
took `4142`, the PSG register programmer; the third took `4228` and `457A`,
which between them pull in `4569`, `4522`, `46D7` and the dispatch handlers.
That leaves the per-frame tick `4015`, the track loader `4BCC` and `4936`.

The third slice is the one that shows what the call-graph table above is
actually for. `4228` and `457A` look unrelated in the profile and share the
whole of `$4705`-`$4882` — the note-to-period conversion and the sample
trigger — reached by a `JMP` from one and a `JSR` from the other. Taking
`4228` first built that tail against a small entry point, and the profile
then showed that `4228` never reaches the sample trigger on this route, so
`457A` had to follow immediately or two hundred lines of transcript would
have shipped unexercised. It is worth checking, after every slice, which of
the code you just wrote the route actually ran.

`4142` is admitted at 1,792 of 3,604 rather than in full, and the reason is
worth carrying to any routine that shares state with an interrupt handler.
`$F5`/`$F7`/`$F9` are the timer driver's per-channel bank bytes — the only
bytes in this bank's working set another thread of control writes. A
transcript is computed once from a snapshot taken before it runs, so a walk
that reads them is only correct if no timer interrupt is delivered while it
runs. The walk declines unless the interrupt mask is already set at entry
(`4142` brackets each voice in `PHP`/`SEI`/`PLP`, so a masked entry stays
masked throughout — 1,326 of the 3,604) or the body finishes inside
`master_cycles_until_timer_interrupt`. Applying the same rule to the already
shipped `49F9` dropped it from 22,664 to 22,622: forty-two calls that had been
admitted on a read that was not provably fresh.

`457A` is admitted at 2,219 of 2,299 for a different reason, and one worth
recording separately: a routine can contain control flow a leaf transcript
cannot express. Its `$82`/`$92` command handler pops four bytes off the stack
and jumps to `$40EE`, abandoning `457A`'s own frame — the sequencer's way of
saying "this voice is finished, resume the caller's caller". A transcript that
has to stop in front of an `RTS` has no way to say that, so those 45 calls
decline. The remaining 35 are handlers this route never reaches, left
untranscribed rather than written blind. Both would disappear if `4015` were
ported, because at that level the escape is ordinary internal control flow.

### Why the tick is where the bank stops

`45:4015` is the obvious next slice and it is not portable. Establishing that
took two profile queries and no code, which makes it the most useful thing in
this section.

The tick composes rather than adds: every routine it calls is already native,
so the new work is about 95 instructions of its own plus `45:4936`. The caps
are fine — 1,058 instructions and 245 writes per call on average, against
1,800 checkpoints and 480 writes, with a measured worst frame of 758 writes
that would decline 9 calls out of 3,599. None of that is the problem.

The problem is the shared-state guard. `4142`'s per-channel loop head at
`45:4148` is `LDA $F5,X`, and it runs 10,812 times across 3,604 calls — three
per call, not the twelve the release path at `415A` suggests. So every
transcript that reaches `4142`, including any transcript for the tick, reads
the timer driver's channel bank bytes, and the whole body has to finish before
the next serviceable timer interrupt. The tick's body is 12,667 master cycles.
The timer period is 5,068 — 254,990 driver entries across 1,292,370,213
cycles. A transcript builder for `4015` would therefore decline all 3,599
calls.

The check is two divisions and it belongs before the disassembly, not after
the transcript:

- **Does the routine read anything another thread of control writes?** Walk
  its subtree for accesses to the shared bytes and use the *execution counts*,
  not the static presence of the instruction. `415A` reads `$F5` on 12 calls
  in 3,604 and would have been easy to dismiss; `4148` reads it on all of
  them.
- **If so, is its body shorter than the interrupt period?** `4142` at 2,054
  cycles is admitted 49.7% of the time, which is close to the 59% a uniform
  arrival would predict. Anything past the period is admitted never.

**Superseded on both grounds, and this one is worth reading in full, because
the section above is the most confident wrong answer in this document.** The
chunking re-screen took it apart:

- **The body is the wrong body.** `45:4015`'s body is a loop. `45:4044` is the
  head, `45:40FF` is a `JMP $4044` that closes it, and the profile gives the
  shape exactly: 32,391 iterations over 3,599 calls, 28,792 continuing, 3,599
  exiting — one clean exit per call. Chunked at the head, the unit that must
  fit the timer period is one voice iteration at **1,137 composed master
  cycles** (12,728,115 of the tick's own instructions plus 24,091,110 of
  already-native callees, over 32,391 iterations). The arithmetic that
  predicted 0 of 3,599 predicts about 78% of 32,391.
- **The voice loop does not reach `4148`.** `JSR $4142` occurs exactly once in
  the bank, at `45:4138`, which is *past* the loop's closing jump. `4148`'s
  10,812 executions are three per call of `4142` — once per tick, in the tail
  — not three per iteration of the voice loop. Every branch in `4044`-`4101`
  targets an address inside the loop or the exit at `4102`. The walk
  accordingly stops in front of `4138` and leaves `4142` to be entered on its
  own, exactly as it is today, with its own guard.

**The second bullet reached the right conclusion by the wrong route, and the
port found out the hard way.** The re-screen that produced it concluded the
loop chunks read no driver state at all. They do: the amplitude commit at
`45:49D2` reads `$20F5,Y`, and both `49B6` and `49F9` run it, so every voice
iteration touches driver state. The recorded rejection was therefore right that
the tick is subject to the guard, and wrong only about which instruction
imposes it — a distinction that would have stayed invisible if the port had not
been attempted.

That makes the section's conclusion wrong for a subtler reason than "it used
the wrong body", and the correction is the useful part. **The guard is a
deadline, not a cap.** Length is not the problem and chunking does not solve it
by making transcripts shorter in the abstract; it solves it by making each
chunk land inside the horizon it was handed. The walk stops at the loop's
closing jump once one more iteration would not fit before the next serviceable
timer interrupt, the core takes the jump and the interrupt, and the next chunk
starts against a fresh horizon. 24,667 of the route's 32,391 iterations now run
inside a transcript, and the tick is native at `+13,017,489`.

What makes this worth its length is that the section was *methodologically*
right — check the blockers before writing the transcript, use execution counts,
two queries and no code — and still produced a stopping point that cost four
slices, because the queries were run against the routine when the contract only
ever constrained a transcript, and because the read they were justified by was
never located. A cheap check aimed at the wrong quantity is not cheaper than no
check.

Five lessons generalise:

- **A call-graph pass is cheap and changes the plan.** Sixteen `JSR` targets
  in 1,078 addresses meant the bank was a set of small leaves, not a monolith.
  That was five minutes of work on an artifact already on disk, and it is the
  difference between an incremental slice and a 10,000-line transcript.
- **Verify a port against an assembly run of the same route, not just the
  baseline hash.** The state census proves the end state; running the
  identical trace ranges with and without the hooks and diffing the artifacts
  proves value, address, order *and* master-cycle offset for every write. It
  costs one extra run and it is the only check that catches a write credited
  to the wrong cycle inside an otherwise correct transcript.
- **Put the stack in the trace range.** The first bank-45 slice passed the
  census, the device-write trace and both configurations while crediting two
  `JSR` return-address bytes 21 cycles late — the core pushes them *before*
  `ADDCYC(6)`, unlike every other store, which lands on its instruction's
  final cycle. Widening the work-RAM range to `$21E0`-`$21FF` found it on
  frame 148 of 3,600, as a constant +21 skew in every subsequent write. A
  narrow "just the routine's own state" range would never have.
- **The same range catches interrupt frames, which is how a status flag gets
  checked.** The third slice's `PLP` at `46AE` published the caller's flags at
  its checkpoint, so an interrupt landing on that exact instruction pushed the
  pre-pop status. Two bytes differed out of 5,458,568 writes, both of them in
  the stack range, and the census matched either way because the handler
  restores `P` on the way out. `PLP` has to defer the mask and only the mask —
  see [the workflow note](NATIVE_PORT_WORKFLOW.md#plp-defers-the-mask-and-only-the-mask).
- **Price the blockers before writing the transcript — against the transcript
  you would actually write.** Two profile queries showed `45:4015` would be
  admitted on none of its 3,599 calls, which turned the bank's obvious next
  slice into a documented stopping point and sent the effort somewhere it
  paid. The effort did pay, and the stopping point was still an artifact of
  pricing a routine the contract never constrains. Price the chunk.

## The palette shadow buffer, and a lumped inventory row

The video inventory listed `00:E93C`–`EBD6` as one 20.6M "VCE palette DMA".
It is six routines with nothing in common but an address range, and splitting
them was the whole of the analysis:

| Routine | Calls | Master cycles | Per call | Outcome |
| --- | ---: | ---: | ---: | --- |
| `00:EB30` | 3,599 | 8,636,040 | 2,400 | Native, 3,599 of 3,599 entered, its `TIA` arm split at `00:EB4D` |
| `00:E9B6` | 672 | 6,548,946 | 9,768 | Native, 672 of 672 |
| `00:EBA5` | 1,121 | 2,629,866 | 2,388 | Native, 1,121 of 1,121 |

| `00:E93C` | 8,969 | 758,370 | 106 | Native, 8,969 of 8,969 |
| `00:E94D`, `00:EA77` | 9 | 140,037 | — | — **superseded**, see the survey below: reachable, but nine calls is not enough evidence to port on |

Three observations worth carrying forward.

**A lumped row hides both the target and the blockers.** Reading the range
top to bottom would have started at `E93C`, the smallest routine in it, and
the first hot loop encountered — `E9B6` at 0.51% — sits in the middle. Ranking
by cycles *within* the cluster took one query and put the three portable
leaves in front.

**Cycles per call is the screen, applied twice.** `00:EAA7` is 1.6M of cycles
and unreachable: 205,012 cycles per call is roughly 17,000 instructions, nine
times the checkpoint cap. `00:E94D` and `00:EA77` are worse — they call the
frame-sync spin, so a transcript for either spans twenty-one frames. Both are
visible from the call graph and the per-call figure alone.

> **Half of that paragraph was superseded, and the half that survived is the
> useful one.** `00:EAA7` is native as of the chunking slice. Cycles per call
> screens out a *transcript*, and a routine whose body is a loop can be more
> than one transcript: the walk stops in front of the branch that closes the
> loop, the core takes it, and the loop head — a second registered address —
> gets the next chunk. Eight calls became 101 transcripts and 1,640,100
> cycles moved. So the screen is real but it rejects the wrong thing: apply
> it to the loop body, not to the call. `00:E94D` and `00:EA77` are still
> correctly rejected, and for the other reason in that paragraph rather than
> this one — they wait on the spin loop, which no amount of chunking shortens.

**100% admission has a cause, and it is worth naming.** The three ported
leaves are admitted on every call because they are leaves in the strong
sense: no `JSR`, no device port, and nothing another thread of control writes.
There is no horizon to miss and no snapshot to go stale, so the only thing an
interrupt can do is land on a checkpoint, which is handled. Contrast bank 45,
where three of ten entries are partial and both reasons trace back to shared
state or to a stack frame the contract cannot express.

There is a cost on the other side of the ledger, and it is new. (It is also
gone: replacements nest as of fork patch `0007`, and a long transcript now
costs the driver nothing. The record below is what the rule was worth.) A long
transcript shadowed the sound driver for its whole body, because the core would
not consult the replacement hook while one was active. `00:E9B6` runs 9,745
cycles and spans about two timer periods, so the interrupts that land inside
it run the driver emulated. The first three leaves added 9,937,182 native
cycles and gave back about 694,000 in lost driver entries — 1,181 fewer than
before, net strongly positive, but the effect scales with transcript length
and should be checked whenever a slice's per-call body is large.

`00:EB30` then made the rule precise by breaking it. It runs up to 18,585
cycles, more than three timer periods, and cost the driver nothing at all —
the 298-routine cycle census before and after differs by exactly one row, its
own. Every call arrives with `I` already set, because the upload has to land
inside the blanking interval. Span is the upper bound on the shadowing cost;
whether the routine runs masked is what turns that bound into a number, and
`--observe-hook` plus the `input_status` column answers it in one run.

The upload itself cost two edits rather than one, and the second is not in
this repository. Adding `$0400`-`$0405` to `is_replaceable_hardware_port` let
the writes through; the transcript then ran three master cycles long per
colour, 102 per block, because the core's wait-state compensation in
`AdvanceReplacementTo` tested only `logical_address <= 0x0003`. `IOWrite`
steals a CPU cycle for the VDC *and* the VCE, so both belong in that test.
Every write value and every write order was already right when the clock was
wrong, which is the argument for diffing traces rather than end state.

### Re-reading the row after the dispatcher split, and a null result

`00:E058` was re-opened by asking which *instruction* was blocked rather than
which routine. The same question was put to this row, whose 1,079,289 remaining
master cycles the inventory carried as "the two fade drivers and the whole-
palette `TIA` arm, blocked". The survey was concrete: disassemble the drivers
and the arm, find every load on the hardware page, and sort each one into
outside input, device state a `peek` could carry, or a read that *changes* the
device — only the third being a wall.

**There is not one load on the hardware page in `00:E93C`–`EBD6`.** The
classification that unparked the dispatcher has nothing to sort here. `00:EB30`
touches `$0402`-`$0405` and every access is a store; the drivers and the shadow
routines never leave work RAM. The row was never blocked by a device read, and
a survey that returns "the question does not apply" is still a survey — it is
what stops the sentence being copied forward a third time.

Measuring the row per instruction, with the deployed registry, says what it is
actually made of:

| | Master cycles | Share | What it is |
| --- | ---: | ---: | --- |
| `00:EB46` | 625,095 | 58% | The whole-palette `TIA`. One instruction, 29 executions, 21,555 cycles each |
| six `RTS` | 302,628 | 28% | The returns every transcript in the family stops in front of, by design |
| `00:E94D`, `00:EA77` | 140,037 | 13% | The two fade drivers |
| the rest | 11,529 | 1% | `00:EAA7`'s chunk boundaries, and resumption where an interrupt landed on a checkpoint |

That table is the survey as it stood. The second row did not survive the next
slice — see *The returns were not a floor* below — and the row now measures
772,635:

| | Master cycles | Share | What it is |
| --- | ---: | ---: | --- |
| `00:EB46` | 625,095 | 80.9% | The whole-palette `TIA`, unchanged and still the wall |
| `00:E94D` | 138,582 | 17.9% | The crossfade driver |
| the rest | 7,440 | 1.0% | Chunk boundaries and resumption |
| `00:EA77` | 1,455 | 0.2% | The fade-to-black driver |
| seven `RTS` | 63 | 0.008% | Three executions the transcripts did not absorb |

Three things follow, and only one of them is a port.

**The `TIA` is a capacity wall, not a semantic one, and it is the cost.** It
moves 1,024 bytes to the two data ports in one opcode against a 512-write
channel, and chunking cannot reach it because a checkpoint is an instruction
boundary and a block transfer has no interior. The arm around it is ordinary,
so it split the way the dispatcher did — `00:EB30` to the transfer, the core
through it, `00:EB4D` after — and `00:EB30` is admitted on all 3,599 calls now.
But the six instructions that moved are 2,523 cycles against the transfer's
625,095. **Reading a wall as an instruction is always the right reading; it
only pays when the instruction is not itself the cost.** At `00:E058` the
unportable instruction was 17% of its block; here it is 99.6% of its arm.

**A quarter of the row was never blocked at all.** 302,628 cycles are `RTS`
instructions the transcripts deliberately hand back, the same convention every
family in the port uses. An inventory row that counts emulated addresses counts
them, and there is no reading of "blocked" under which they qualify.

### The returns were not a floor

The paragraph above stopped one step short. "Not blocked, it is the convention"
is a true statement about why the cycles were there and an unexamined one about
whether they had to be, and the convention turned out to be a habit rather than
a constraint. **A transcript can end past its own `RTS`**, and the palette
family is where that was established:

- the core never relates a resume address to the entry address, at the install
  site or at a checkpoint;
- the stack is ordinary work RAM at `$2100`, so the return address is two bytes
  the entry already carries — low at `$2100 + S + 1`, high at `$2100 + S + 2`,
  land on that word plus one, `S` up by two;
- and delivery is unmoved, because the final checkpoint samples, advances,
  assigns the caller's address and pops the frame before the loop reaches
  `DcSelectInterrupt` — the same boundary at the same cycle.

`RTS` **emits no write**, which is what makes it checkable rather than merely
arguable: nothing in a trace is allowed to move. Nothing did. All three golden
artifacts held, in the family regression and in the whole-registry census, and
the Debug route reproduced all three byte-for-byte. 14,369 returns absorbed,
**+301,749 native master cycles** (671,640,741 → 671,942,490, and 14,369 × 21
closes it exactly), and the seven return addresses fell from 302,628 cycles to
**63** — three executions reached by interpretation rather than through a
transcript.

The lesson is narrower than "audit the conventions". It is that *the reason a
cycle is emulated* and *whether it has to be* are two questions, and answering
the first is not answering the second. This row had already been re-read once
for exactly that mistake.

There is a second lesson, learned a slice later. "Nothing in a trace is allowed
to move, and nothing did" was true of every trace the family regression takes,
and false of one it does not: `--routine-call-trace` completes a call on an
emulated `RTS` boundary, and absorbing the return deleted the boundary it waits
for. Traced afterwards, `00:E93C` reported its first call as returning to
`01:CAB6` after 53,486,487 cycles rather than to `00:F0FE` after 78. A
transcript now declares the return it absorbs so the observer can close the call
where the assembly did; see *An absorbed return has to be declared* in
`NATIVE_PORT_WORKFLOW.md`. Checking that a change moves nothing is only as good
as the set of things being watched.

There is a third, from the rollout that followed. Bank `03`'s eight owning
families now absorb their returns too, taking the bank from 2,552,511 emulated
return cycles to 1,498,290 and the route from 8,957,280 to 7,599,885 — but the
ranking that ordered that work is not a work queue. A return is only absorbable
by the walk that owns it, and `03:603E`, the second-largest row left in the
bank at 137,607 cycles, belongs to a parent at `03:6005` that has never been
transcribed. A survey of emulated `RTS` rows measures a *pool*; what is
addressable in it is whatever already has a ported owner.

Bank `08` then made the same point from the other end. Its 1,726,353 cycles
were 95% two addresses, both ending walks that were already native, so two
edits took the bank to 92,742 and the route to 5,966,274 — more than the eight
families of bank `03` put together. The size of a bank's pool says nothing
about the work it will take; the number of ported owners in it says everything.

**The drivers are reachable and still not worth porting, for a reason about
evidence.** The old note — that calling the frame-sync spin at `00:E321` forces
a transcript to span twenty-one frames — is wrong in exactly the way the
dispatcher's note was wrong: a walk stops in front of the `JSR`, the core takes
the spin, and the return address is the next entry point. `00:E94D` has a
second such instruction of its own, the `TII $27B9, $27BA, $03FF` at `00:E950`,
1,023 work-RAM writes and 18,465 cycles, which splits the same way. What stops
them is that this route enters `00:E94D` **once** and `00:EA77` eight times.
Every entry point in this family is admitted on hundreds or thousands of calls,
which is what lets a regression claim the transcript is state-generic rather
than a transcription of one observed path. One sample cannot make that claim,
and 0.011% of the route does not justify lowering the bar. That is a different
verdict from "blocked" and it should be recorded as a different word.

## The bank-switching call wrappers, and two corrections

`00:E0EB`–`E292` was the next lumped row: 15.3M, "VBlank handler and pad
reader", with a plan attached that said to widen the write channel to reach
the joypad at `$1000`. Splitting it by call graph before reading any
instructions turned one row into eight routines:

| Routine | Master cycles | Outcome |
| --- | ---: | --- |
| `00:E195` pad reader | 6,929,670 | Blocked: reads `$1000` |
| `00:E241`/`E255` banked call | 2,878,650 | Native, every call |
| `00:E111`–`E13F` VBlank body | 2,412,678 | Native, every call |
| `00:E262` trampoline | 953,343 | Native, every call |
| `00:E140`–`E178` VBlank epilogue | 821,685 | Native, every call |
| `00:E058`–`E0EA` dispatcher | 769,938 | Native either side of its `LDA $0000`: 640,374 |
| `00:E0EB`–`E110` VBlank prologue | 544,104 | Native, every call |
| `00:E219` bank pair | 501,639 | Native, every call |
| `00:E1FD`/`E20D` asset resolver | 377,085 | Native, every call |

The first correction is that the plan's prescription was aimed at the wrong
side of the bus. `00:E195` writes `$1000` to strobe the pad and then **reads**
it back, and `00:E058` opens by reading the VDC status register. A replacement
callback receives work RAM and registers, so nothing on an allowlist reaches
either. Almost half the row was written off as phase-2 device-model work, and
the write channel never came into it.

Both halves of that write-off were wrong, and both were wrong in the same way:
the row names routines, and what was blocked was an instruction. `00:E195`
went first — what the joypad answers is computable from the frame's pad state
and the latch lines the routine drives itself. `00:E058` went four slices
later, split in front of its `LDA $0000`: above the read, four register saves;
below it, a dispatch on a byte already sitting in the accumulator. 640,374 of
the row's 769,938 cycles are native, and the 129,564 that are not are the one
instruction whose read *is* the interrupt acknowledge — a side effect the
write channel has no way to reproduce. **When a row says a routine is blocked,
check whether the block is really the whole routine.**

What went instead was the bank-switching linkage — the three wrappers here plus
the two at `00:ECC6` — nine entry points, 52,911 calls, 4,849,479 cycles,
admitted on every call. They are the first transcripts in the port to change
the bank mapping, which turned out to need no new capability: `CpuRegisters`
already carries all eight `MPR` slots and a checkpoint already applies them.

The second correction is to the shadowing rule two sections up. These
transcripts are 36 to 162 master cycles each, and they cost the sound driver
1,326 entries and 756,342 cycles — 15.6% of the slice's own gross, the largest
bill any slice has paid. Per-call length is not what the cost scales with;
total native time is, because what the driver loses is proportional to how long
the hook is unavailable. `native cycles / interrupt period` predicts 739 here
against 1,326 measured, which is the right way to budget it. Masking still
decides which cycles are free: the three wrappers that run inside the VBlank
handler cost nothing, and the whole bill comes from the six on the main thread.

The bodies followed in the next slice and closed the row: six entry points
around the calls the core keeps, 13,932 calls, admitted on every one. Splitting
the row was the whole of the difficulty — once the dispatcher's `LDA $0000` was
isolated as its own routine, everything below it was ordinary transcription
against ports the channel already carried.

Its shadowing bill is the counterweight to the paragraph above: 64 driver
entries and 36,330 cycles, 2.7% of its 1,350,720-cycle gross against the
wrappers' 15.6%. The rule holds — the wrappers are six times the native time —
but it is worth seeing both ends of the range before budgeting a slice on it.

## The graphics upload paths, and lifting the routine-length ceiling

`00:E3C0`–`E47C` was the next row, and screening it took one pass: every load
in it is immediate, zero page, or through the source pointer at `$2F`/`$30`.
Nothing reads a device register, so the whole 7.0M was phase-1 work rather
than half of it. Three routines — a VRAM clear, a VCE colour-table clear, and
the generic word-stream decoder at `00:E41F` that is 6.9M of the 7.0M.

The decoder was the first thing in the port too large to be a transcript at
all. One call is 167,000 master cycles: 3,400 port writes and 12,400
instructions against a channel of 512 writes and 2,048 checkpoints. That is
not a screening result, it is an arithmetic one, and it is worth doing before
reading any instructions — `00:EAA7` was set aside two slices ago for exactly
this reason, and chunking is what eventually collected it.

The answer is to chunk, and it needed nothing new in the core. Give the
routine a second entry point at the head of its loop, and stop the transcript
in front of the backward branch that closes the loop rather than at an `RTS`.
The core executes that branch, lands on the loop head, and calls the
replacement again. The hook already fires on any fetch at a registered
address; a replacement already ends by handing one instruction back. Two
properties make it safe:

- **Progress.** Every chunk must transcribe at least one iteration, or the
  core re-enters at the same address with the same state for ever. Deciding
  where to stop by budget instead of by count is what guarantees it: read the
  next record's size before committing to it, and take it whole if it fits.
  The first record of a chunk is always taken, so a chunk can never be empty.
- **Cost.** The leak is the branch itself. Here it is eighteen master cycles a
  chunk — the `BRA` plus the `CLY` behind it — across about 350 chunks, or
  5,868 cycles of the 6.9M.

The 41 decoder calls become 41 head transcripts and 326 continuations,
admitted on every one. The routine-length ceiling is now a budgeting question
rather than a limit, which changes what is worth screening in the rest of
phase 1.

The other precondition was shared state, and it is the one worth copying. The
decoder reads `$2F`/`$30`, which is the game's general-purpose source pointer,
written from some 340 sites across eight banks. A snapshot-based transcript is
only sound if nothing writes it underneath, and with a pointer that widely
shared the presumption has to be that something does. Measuring it is cheap:
bracket each call in an assembly write trace between a store only its header
makes and its last data-port write, and count foreign writers inside the
windows. All 23,300 writes to `$2D`-`$30`, `$37` and `$38` inside the 41
windows come from the decoder itself. Do this before writing the walk, not
after the census diverges.

The shadowing bill runs the opposite way to the two slices above. These are
main-thread transcripts averaging 18,000 cycles — more than three timer
periods — so the interrupts landing inside them cannot reach their own hooks:
6,908,844 native cycles cost 317,196 elsewhere across 956 entries, 4.6% of
gross, and the loss is on the interrupt side (130,122 in the sound driver,
165,123 in the music sequencer) rather than in the driver alone. Four slices
in, the rule looked stable: the bill tracks total native time, and which side of
the interrupt the transcripts run on decides who pays it.

## The tilemap upload, and the limit of the checkpoint shape

`00:F261`–`F4F1` is the other half of the same driver and the last coherent
video row in the ranking. Screening was the same three questions and gave the
same three answers — no device reads anywhere in the region, every load
immediate, zero page, absolute or through one of three pointers, and every
pointer resolvable from the live MPRs — so the whole 5.7M was phase-1 work.

It also needed none of the previous slice's machinery. The row writer at
`00:F3E7` is 32 words a call, 168 writes and about 660 checkpoints against a
channel of 512 and 2,048, so nothing chunks. What it needed was entry points:
the driver makes six calls, a transcript stops in front of a call, so six of
the ten entries are just return addresses. Two of those calls land on
`00:E20D`/`00:E200`, native since the wrapper slice, so stopping there re-enters
that module rather than transcribing eleven instructions twice.

The finding is the other two entries, and it is a limit of the contract rather
than of the code. A checkpoint expresses one shape — advance to the sample,
sample, advance to the end — and it fits every instruction whose core macro is
`GetXX(EA); ADDCYC(n); LastCycle(); …`. `BBR` is `LD_ZP` wrapping `JR`: it
samples twice and crosses in four clock steps. The interrupt outcome at the
instruction boundary is the same either way, so this does not show up as an
interrupt-timing bug in the walk. It shows up because those steps are where the
core tests `next_event`, and running the video `EventHandler` one step later
shifted a VDC event enough to move a timer interrupt by one instruction, four
times in 3,600 frames. Two of the four were in assembly *downstream* of the
walk. The fix is to hand `00:F423` to the core and register the two addresses
its arms arrive at, which is why the loop has 17,248 entries rather than 539,
and why 365,664 cycles — 77% of what is still emulated in the region — stay
emulated.

Shared state was measured again, and the previous slice's bracketing trick had
to be replaced. It works when the only way into a region is a call to its head;
it fails here because `00:F43D`, `00:F48D` and `00:F4DF` are also reached
independently, and a window inferred from the writes ran thirty times too long.
Take the boundaries from an `--observe-hook` call trace instead. Across 2,649
exact windows, 92,978 writes are the routine's own and the only others are
interrupt frames below the live stack pointer.

The shadowing bill was the largest any slice had paid: 5,180,931 native cycles
cost 937,827 elsewhere across 1,717 entries, 18.1% of gross, 923,088 of it the
sound driver's. Net `+4,243,104`. That beats the bank wrappers' 15.6% on a fifth
less native time, so the rule above needs a correction rather than a fifth
confirmation. Total native time sets the scale, but the shadow window is wider
than the transcript: a driver entry that lands inside one runs emulated *while
the transcript stays suspended*, so its 563 cycles are shadowed as well, and
anything arriving inside those is shadowed in turn. Expect the bill to run
higher than the transcript's own share of the route whenever the transcripts are
main-thread and unmasked, and measure it with a `--registry-exclude` run rather
than predicting it.

## The collision frame, and the price of a call

`01:CA84`–`CDF7` is the code around `01:CC1A`, which the ranking had shown as a
"collision tail" row ever since the scanner itself went native. Screening gave
the same three answers again — no device reads, every load immediate, zero page,
absolute or through a pointer resolvable from the live MPRs — so all 8.4M was
phase-1 work, and the walk needed nothing the previous four slices had not
already built. Nineteen entry points, admitted on every call, `+3,232,335` net.

Two things in it are worth carrying forward.

The first is what the ranking was hiding. `01:CD74`, the playfield-tile probe,
had no row of its own because it sits outside the `CA84`–`CC04` span the
inventory had been quoting, yet it was 2,643,867 cycles — two thirds of the
family and a pure leaf that makes no calls at all. It is the largest single
piece of logic phase 1 has ported through one entry point, and it was invisible
because the inventory row had been drawn around the wrong addresses. When a row
looks small for what it is called, re-derive its span from the profile before
believing it.

The second is what stays behind. Eleven of the nineteen entry points exist only
because a transcript stops in front of a call, and the calls themselves are not
free: `01:CB5E` is `JSR $CC1A` and `01:CC40` is the `RTS` that returns from it,
and the sweep crossed that boundary 84,735 times for 3,592,728 master cycles.
Both sides are native. The loop between them is native instruction for
instruction. Those cycles were 42 per crossing of pure contract overhead, and
they were larger than the logic they surrounded — the `CA84`–`CC04` row fell
from 3,974,346 to 2,399,445, and 1,795,419 of what was left was that one `JSR`.
The next slice composed it away; see below.

Shared state was measured on exact windows again, and the analysis is worth
reusing verbatim: rank each foreign writer by the fraction of its executions
that land inside a window. Callees score near 100% because they only run there;
asynchronous writers score near zero because they are uncorrelated. For this
family the split was absolute — eighteen arithmetic instructions at
`00:E56E`–`00:E847` between 99.3% and 100%, and every one of the three hundred
other writers of the same addresses at exactly 0.00%. That is a stronger
statement than "the writers I found were the routine's own", and it costs
nothing extra once the windows exist.

The shadowing bill is the largest in proportion so far: 4,091,373 native cycles
cost 859,038 across 1,548 entries, 21.0% of gross, 815,580 of it the sound
driver's. That is a *higher* rate than the tilemap's 18.1% on a fifth less
native time, which is the second consecutive slice to move the ratio the wrong
way. Total native time sets the scale and nothing more; the ratio is a
measurement, not a prediction.

## Composing a call, and what it costs the driver

The call boundary the section above named is gone. `01:CB48` no longer stops in
front of `JSR $CC1A`: it transcribes the call, splices the scanner's own
transcript in where the core would have run it, transcribes the `RTS`, and
hands control back at `01:CB61` with the scan answered. `01:CB5E` falls from
1,795,419 master cycles to 17,622 and `01:CC40` from 1,797,309 to 19,776, and
`01:CB48` becomes the largest single native address on the route at 7.96% of
all master cycles.

Screening had nothing to do this time — the callee was already ported, proven
and byte-exact, and composition changed neither what it computes nor what it
writes. The two things it did need are worth remembering. The child reads work
RAM as it finds it, so it has to be handed a staged copy carrying the parent's
own writes; and it can return from somewhere the parent cannot resume from, so
the composition has to be an attempt that rolls back. 83,905 of the scanner's
85,715 calls compose. The 1,810 that do not are the hit path, which leaves the
scanner at `CCD2` or `CCD4` with no `RTS` to transcribe, and for those the walk
truncates its own vectors back and ends in front of the call exactly as before.

The bill is the interesting half. Gross was exactly the tax — 83,905 × 42 =
3,524,010, the one figure in this document that was safe to predict, because a
`JSR` and an `RTS` cost 21 each whatever surrounds them. What was not
predictable is that a composed walk is a *longer* transcript, so it is
suspended across more timer interrupts, and every driver entry that arrives
while a replacement is active runs emulated. `00:FC00` lost 1,184 admitted
entries and 683,271 native cycles; sixteen other routines lost 11,790 between
them; 695,061 in all, 19.7% of gross, against the collision frame's 21.0%. Net
`+2,828,949`.

Four to one is a good trade, but the ratio is a property of this call, not of
composition. It holds because the call sits in a loop whose body is short, so
42 cycles was a large share of the region. Around a long body the tax is noise
and the extra shadowing is not, which is the same lesson as the paragraph above
it: measure the bill, do not carry it forward.

## The Sorcerer tick, and the cleanest screen yet

`02:586F`-`02:5903` in bank 02 is the Sorcerer's per-frame tick, the largest
block of unported gameplay left on the route and the only block of its size
with no native entry anywhere inside it. One routine in three pieces, split by
the two calls it makes to the collision-table interpreter at `03:6966`: the
staggered deployment delay on the sixteen-bit countdown in `$3B00,X`/`$3B80,X`,
the arrival state that reseeds the table cursors when the interpreter reports
its terminator, and orbit, which reads a four-entry difficulty table out of the
bank's own ROM page and copies the interpreter's event record from `$3A80,X` to
`$3980,X`. Five entry points, admitted on every call, 3,156,294 gross and
`+2,595,360` net.

The screening is what to take from it. Ninety-nine instructions across seven
banks write the addresses this family reads. Ranking them by the fraction of
their executions that land inside one of the family's exact call windows put
**one** of them above zero — `03:69D9`, the interpreter's own event store,
which is the family's callee — and the other ninety-eight at 0.0%. Not "close
to zero", and not "the writers I found were the routine's own": zero, for every
writer that is not the callee. Two slices ago the same method produced a split
with eighteen callees at 99.3-100% and three hundred others at 0.00%. That is
now the expected shape of the answer, and a middle band is the signal that
something needs looking at.

There is a corollary worth stating. A window that contains a call contains its
callee's writes too, so a callee scoring high is not evidence of a problem —
it is evidence the window is drawn correctly. What matters is that nothing
*else* is in there.

The region is 4,055,142 down to 910,530, and about 87% of that remainder is the
same leaf-contract tax the collision frame ran into: two calls to the
interpreter, two to the bank-01 wrapper at `$C018`, and three `RTS`
instructions. Composing the interpreter is the obvious next move and the reason
to be careful is measurable: `03:6966` is an atomic body rather than a
checkpointed transcript, and it already declines 2,850 of its own 34,259
entries at an interrupt horizon. Splicing it into a longer parent puts that
uncheckpointed stretch inside the parent.

## Ranking by routine, not by region

The three largest single routines on the census route with no native entry
anywhere inside them were `01:C8F3` (1,743,819 cycles with its neighbours),
`01:DAF8` (1,508,400) and `01:C969`. None of them appeared in the inventory in
[EMULATOR_ELIMINATION.md](EMULATOR_ELIMINATION.md), because that table groups
by adjacent address range and each of these sits alone. A region-ranked view
had the phase looking thinner than it was.

**Rank the profile two ways.** Cluster addresses into regions to find families,
and sort routines individually to find isolated ones. The clustering step wants
a gap threshold; `0x20` separated these three cleanly from their neighbours,
where `0x40` merged them into ranges dominated by already-native code and hid
them completely.

They have nothing in common but a shape — straight-line integer arithmetic over
work RAM and zero page, ending in an `RTS`, with no call, no device register
and no bank change — and that was enough to make them one walk. 3,066,105 gross
and `+2,439,807` net across 7,472 calls, admitted on every one.

The screen found no foreign writer at all: of 358 instructions that write any
address the three read, exactly four ever write inside a call window, and all
four are `01:C8F3`'s own stores. The Sorcerer tick had one in-window writer and
it was its own callee. These have none, because they have no callee — which is
what the screen should say about a leaf, and is worth knowing as the shape to
expect when the answer is "nothing shared".

### A rejection that did not survive the method

`01:DAF8` is in this document twice already, rejected both times. The wording
was that its "cycle, write, and result populations remain mixed rather than
exposing a stable state-derived return", and that the pair should stay
assembly-backed "until a naturally observed child branch can be isolated".

That was the right answer for the method in use then. Replay-based screening
had to find a return value the replacement could *predict* from the entry
state, so a routine with two exits and a wide cycle distribution was genuinely
unusable. An instruction-boundary transcript predicts nothing — it executes the
branches the data selects and stops in front of whichever `RTS` it reaches — so
a mixed population is not an obstacle, it is two exits and a `case` label for
each. The calls divide 1,459 through `01:DB9D` and 680 through `01:DB81`.

**Re-read old rejections when the method changes.** This one had been standing
since before transcripts existed, and it was blocking 1.5M cycles the whole
time. The rejections that stay valid are the ones that name a *structural*
reason — a device read, a call the transcript cannot contain, a body longer
than the caps — not the ones that name a property of the data.

> **The last item in that list is wrong, and it was wrong when it was written.**
> "A body longer than the caps" is not a structural reason, because the caps
> bound a transcript and a routine whose body is a loop can be as many
> transcripts as it needs. That clause is the sentence that kept `00:EAA7`
> rejected for three slices and `45:4015` for four, and both are the same
> mistake this section was written to warn about — measuring a length against a
> cap and reading the answer as a property of the code. The structural
> rejections are the ones where **no cut point exists**: a device read, a call
> the transcript cannot contain, a wait on another routine's loop (the two
> fade drivers at `00:E94D` and `00:EA77`, which spin for twenty-one frames),
> or a single instruction that overruns a channel by itself — `00:EB30`'s
> whole-palette `TIA` moves 512 bytes in one opcode, and a checkpoint can only
> cut at an instruction boundary, so there is nowhere to put the cut. Length
> is a budgeting question. Ask where the loop head is before calling it
> anything else.

## Use on future families

Follow the command and interpretation rules in
[the native-port workflow](NATIVE_PORT_WORKFLOW.md#fallback-hotspot-profiling).
Create an observer set containing the current parent and two to five likely
siblings or continuations. Compare matching recording plans only; do not
combine Debug and Release copies of the same route. A routine marked `Native
registered` can still reject an unimplemented state and safely fall back to
assembly, so inspect its transcript before treating it as fully covered.
